## 问题

开发阶段如何按影响面验证并沿用同输入证据，同时保留原生执行、固定准入集合和全量验证各自的责任？

## 背景与执行事实

测试执行和验证结论有不同的权威。原生 runner 与 ADR-0184 的进程监护机制观察实际执行、退出和资源收束；证据消费者判断这些事实是否满足目标单元的验证义务。源码提交号、程序路径或成功计数均不能单独证明同输入或完整执行。

| 实体 | 权威与边界 |
|---|---|
| 原生单元和声明 | Cargo/nextest、SQL runner、System runner 与具名阶段定义原生身份、运行输入、复用范围和初始状态合同 |
| 执行方记录 | 在真实生命周期开始、结束时采集输入和实际验证方式，逐项保存结果、退出与清理事实 |
| 影响面选择 | 开发阶段选择及解释作者义务；不改变准入成员 |
| `Observation` 与 `Scope` | 分别保存事实与目标范围；身份匹配不等于可复用 |
| `compose` | 只读消费所有观测，独立派生覆盖、反例、清理义务和层结论 |
| 处置登记 | 为精确单元的稳定失败特征提供 owner、原因、到期边界；不重写原始结果 |

Rust 测试可执行内容与其声明的运行期输入参与身份；SQL/System 还绑定实际被测程序、runner、有效配置、拓扑与声明的 fixture/environment。SQL 默认以整个 suite 生命周期为复用范围；没有明确初始状态合同的更细范围不能从若干成功行中推断出来。

## 考虑过的选项

1. **每次开发修改都运行完整固定集合。成本否决。** 简单且不需要历史复用判定，但代价随工作区增长，反复支付外部进程、fixture 和未受影响领域的成本。固定准入和全量仍提供独立兜底；它们不成为每次开发迭代的默认动作。
2. **用最近一次 PASS、提交号或退出码缓存单元结论。设计否决。** 记录少、查询快，但会丢失同输入反例、部分执行、验证开关变化和未完成清理；它无法满足可追溯的证据语义。
3. **让组合器重新定义执行格式或补造原生终态。设计否决。** 能简化消费者适配，却会制造第二个退出与资源事实权威，破坏原生 owner 的责任。
4. **分层验证、执行方采集身份、消费者只读组合。采用。** 需要维护声明和原生格式适配，但允许独立审查选择理由、事实完整性及复用资格。

## 裁决

1. **原生事实唯一权威。** runner/监护机制拥有执行与收束；组合器只生成派生记录，不改写 JUnit、原生索引、SQL/System 结果或实际退出。进程外资源由创建 owner 在副作用之前登记并带回真实清理结果。
2. **先定成员，再看观测。** 开发按影响面选择；准入采用原生默认固定集合与明确处置；全量包含全部定义单元和必需模式，只接受本轮执行。普通测试不能代替 Loom/Miri 等另一模式。
3. **五维分开表达。** 来源、原始结果、完整性、适用性和处置独立保存。取消、未知、缺失或清理失败不能因已知失败登记而变成覆盖成功。
4. **复用依赖实际输入和完整生命周期。** 正面证据必须满足身份确认、实际验证义务、原生复用范围、初始状态合同、执行终结及必要清理。suite 原子取源；不同生命周期的部分成功不能拼成完整 suite。执行中输入变化或声明不足时不复用，不猜测未来私有 runtime 身份。
5. **保留全部反例和清理义务。** 同输入一败一过判为不一致，不能取最新或最好一次。取消后的新完整执行可以补覆盖；旧事实仍保留，独立清理义务须有准确 owner 的确认，其他资源成功不能解除它。
6. **处置只覆盖登记的失败。** 已知失败按精确单元和稳定特征匹配，不用日志猜码。独立 oracle 失败、未执行的验证义务及 case/suite 清理违约均保留；准入层的隔离可以排除单元断言门禁，不能隐藏其清理失败。
7. **开发延后必须可见。** 已有逐项 Rust 义务时，开发阶段可明确延后重复的工作区聚合阶段，写明理由和准入兜底，不缩小逐项义务。仅剩 doctest 而原生正常 batch 要求非空 nextest 时，具名记录一次正常 batch 重复已满足范围的例外、实际过滤器和来源；保留重复执行的新失败，不合成 doctest-only 原生索引。

## 接受的妥协（诚实记录）

声明和 producer/consumer 接口增加维护成本。保守身份或初始状态不足会减少可复用范围；为避免误判，宁可显示缺口，也不从路径、标签或部分日志补造身份。开发结论只覆盖相应部分，不能冒充准入、全量或正式来源。

原生执行接口保持独立，因此 doctest-only 续跑暂时支付一个已满足范围的重复成本。已知基线反例、未确认清理和未覆盖可能长期存在；本机制负责真实呈现和精确处置，不承诺把产品矩阵变绿。某次任务的有界验收不自动修改通用组合规则。

## 何时重新评估

- 原生执行 owner 提供独立 doctest 接口并明确其选择、退出和清理合同后，重新评估正常 batch 重复成本，不能由消费者先模拟接口。
- 原生 owner 能为更小范围提供可验证的隔离、重置或不可变状态合同后，再缩小 suite 等复用范围；同步验证输入变化、部分执行与清理边界。
- 正式尝试来源或共享证据服务落地后，明确其身份、保留和恢复责任；在此之前，本地材料保持本地来源，不因发布 PR 自动晋升。
- 工作区规模、外部执行成本或准入完整性要求变化时，重新评估开发扩大策略和完整固定集合的成本取舍；成员改变必须先有明确规则，不能按本次结果挑选。
