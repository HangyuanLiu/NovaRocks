# 技术概念讲解

把讲解请求作为独立的只读理解任务。先铺平必要概念，再沿因果链推导结论；不要从结论或源码名词堆开始。

## 守住范围与证据

1. 完整读取 `../workbench/references/workflow-contract.md` 和适用的 `AGENTS.md`。
2. 保持只读：可以检查代码、spec、plan、ADR、PR 或日志，但不修改文档和代码，不创建 goal，也不进入 spec、plan、
   execute 或 finish。用户随后明确要求产出或修改时，再交回对应阶段 skill。
3. 判断主题属于哪类，并据此取证：
   - 通用概念：解释稳定定义、动机和机制；
   - 当前系统或代码：核对真实调用链、数据结构、配置和测试，以当前代码为准；
   - spec、plan、PR 或架构变化：分别核对变化前、目标态和当前已落地状态，不把目标文档当成现状；
   - 故障或异常：区分已证实根因、证据支持的怀疑和仍缺失的证据。
4. 回看本次对话中已有说法。发现此前表述不严谨、过度简化或影响范围被夸大时，先明确修正，再继续解释。
5. 关键事实无法确认时直接说明不确定性和缺少的证据；不要用教学类比或合理猜测替代事实。

## 先搭建讲解地基

按照用户对内部原理基本不了解来组织内容，但不要把用户当成没有判断力：

1. 先说明理解主题需要哪些前置概念，以及这些概念之间的关系。
2. 开头只给学习路线和问题背景，不使用“一句话结论”“先说结论”“核心就是”等方式提前收束。关于根因、对错、
   bug / 设计或必然 / 可避免的最终判断，放到机制推导之后。
3. 技术术语首次出现时写成“中文解释（English Term）”；用户问题里已经出现的术语也不例外。`FE`、`BE` 等缩写
   首次使用时先解释全称和职责，后文再使用缩写。
4. 先解释“为什么需要它、它解决什么矛盾”，再解释“它是什么、怎么运转”。
5. 每引入一个新机制，都回答它依赖什么、改变了什么状态、为什么这样设计、失败时会怎样。
6. 在读者已经具备必要概念后再给最终结论，让结论成为前文因果链的自然结果。

## 贯穿一个具体例子

尽早建立一个贯穿全文的示例，并在后续每一层继续使用同一个例子：

- 给出具体角色、输入、数字、拓扑或时间顺序，例如 1 个协调节点、3 个执行节点、1,000 万行数据和 128 MB
  内存上限；不要只写“假设有一些数据”。
- 明确示例的初始状态、每一步输入、发生的变换、输出状态和下一步依赖。
- 解释 plan 变化时，用同一输入展示变化前后节点、所有权或执行顺序；解释数据流时，跟踪同一批数据或同一个请求；
  解释生命周期时，跟踪同一个标识和状态转换。
- 类比用于建立直觉，具体示例用于验证逻辑；两者都不能代替真实机制。
- 为讲解而省略并发、失败恢复、分布式拓扑或边界条件时，明确标注“教学简化”，随后补充真实系统中的差异。

不要中途更换成互不相关的例子。确需扩展示例时，先说明新场景与原示例的映射关系。

## 强制拆开容易混淆的层次

对每个关键现象分别说明：

1. **概念层**：由定义或基本约束决定的部分；
2. **设计层**：系统主动选择的契约、所有权和失败语义，以及可选替代方案；
3. **工程实现层**：当前代码如何实现，哪些只是目标态或尚未落地；
4. **结果影响层**：对正确性、性能、资源、可运维性或用户行为的实际影响。

遇到以下问题必须直接分类，不要混写：

- 这是 bug、符合设计的行为，还是证据仍不足；
- 这是理论上必然，还是当前实现可以避免；
- 这是概念限制、产品裁决，还是受时间、兼容性、性能或维护成本约束的工程权衡；
- 这是当前状态、目标状态，还是仅供讨论的提案。

多方案、多系统或变化前后存在 2 个以上稳定比较维度时使用表格；比较维度不清楚时先用因果说明，不为形式强行制表。
当 3 个以上步骤、分支或所有权关系用文字难以看清时，可以增加一张紧凑流程图，但仍要用正文解释关键因果。

## 保持中文表达自然

- 全程使用中文句子。标准技术专有名词、代码标识符、协议名和必要缩写可以保留英文，阿拉伯数字正常使用。
- 避免为了显得专业而中英文来回切换；已经给出中文解释的术语，后文不要无意义地换称呼。
- 使用清晰的小标题和短段落。先讲直觉，再讲机制和证据；不要把源码路径列表当成解释。
- 引用代码时说明该代码在因果链中的职责，并给出可核查的文件与行号；只展示真正帮助理解的少量片段。
- 类比必须指出哪里相似、哪里不相似，防止读者把类比当成系统真实结构。

## 讲清理想与现实

同时说明理想方案和现实约束：

- 理想模型在没有历史兼容、资源上限或交付约束时会怎样设计；
- 当前系统受哪些兼容性、性能、复杂度、风险或迁移成本限制；
- 现有取舍换来了什么，又牺牲了什么；
- 哪些限制是长期契约，哪些只是当前实现状态，哪些后续可以改进。

不要只给理想答案，也不要把“当前就是这样”包装成必然正确。

## 推荐组织顺序

根据主题调整篇幅，但默认依次覆盖：

1. 理解路线和必要前置概念；
2. 贯穿全文的具体示例；
3. 从输入到输出的逐步机制；
4. 概念、设计、实现和影响的分层；
5. 当前代码或文档证据；
6. 常见误解、此前说法修正和教学简化边界；
7. 替代方案及理想与现实的权衡；
8. 从前文推导出的结论。

不要机械保留空章节；合并不适用的部分，但不能省略影响结论的因果环节。

## 结束方式

结尾必须：

1. 用一小段收束核心因果，而不是重复全文；
2. 问用户“哪一段还没绕明白”；
3. 按概念列出 3 至 6 个可以继续拆解的入口，例如“所有权边界”“状态机”“数据如何跨进程”“失败恢复”或
   “为什么不用另一种方案”，不要只列源码文件名。
