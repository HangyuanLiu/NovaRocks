# 写 Spec

把已接受的设计固化为项目文档。不要在这个阶段继续发明关键设计，也不要写实现 plan 或代码。

## 前置检查

1. 完整读取 `../workbench/references/workflow-contract.md`。
2. 读取 `AGENTS.md`；按 contract 从当前请求 / memory 解析 `DOC_ROOT`，无可用记录时回退到仓库
   `docs/workbench/`。
3. 读取 `DOC_ROOT` 和目标子目录下适用的 `AGENTS.md`。
4. 确认存在明确接受的设计摘要。
5. 对摘要中的当前行为、缺口和代码锚点重新核实。
6. 搜索活跃文档和归档文档，避免重复立项或覆盖已有决策。
7. 若仍有会改变目标、外部契约、所有权或失败语义的未决项，停止写作并回到
   `$dev-workflow-discuss-design`。

## 选择文档类型

- 一个可独立实现、一个 PR 粒度的执行单元：写入 contract 或适用 `AGENTS.md` 规定的 spec 目录。
- 会派生多个独立 spec 的长期工作线：写入 contract 或适用 `AGENTS.md` 规定的 umbrella 目录。
- 文件名遵循 `YYYY-MM-DD-<kebab-slug>-design.md`。

参考 `assets/spec-template.md` 或 `assets/umbrella-template.md`，并按 contract 调整 frontmatter；项目启用
roadmap / umbrella 时，再维护 Roadmap、子任务面板和阶段依赖图。
将模板落盘时，把标题、字段显示名和占位文字转换为当前请求与适用 `AGENTS.md` 要求的文档语言。

必要时使用 sub-agent 独立核查代码证据、文档重复项或 wikilink 完整性；最终文档由主 agent 汇总并校验。

## 先让评审者理解任务

Spec 的读者可能没有参加前面的讨论。开篇用短段落回答：本次要做什么、谁在什么场景遇到什么问题、为什么现在要做、
完成后会得到什么。然后说明设计目标及本次边界。不要用版本沿革、裁决编号或源码符号列表代替任务介绍。

需要解释技术概念时，借用 `../dev-workflow-explain-technical-concept/SKILL.md` 的讲解方法：先解释必要术语的职责和
关系，尽早给出一个具体场景，沿同一输入追踪状态、交接和输出，用因果说明机制与取舍。只读旁路的阶段限制和对话式
结尾不移植到 spec；本文仍按已获授权的写作阶段执行。只解释理解设计所需的概念，不扩成通用教程。

主体沿问题展开：现状为何产生问题 → 目标行为如何改变体验 → 内部机制如何支撑行为 → 失败时如何保持约定 → 如何验证。
段落之间说明因果或依赖，章内子标题可以使用该任务的实际概念。流程图用于看清状态和交接，表格用于比较方案或接口，列表用于
少量并列事项；不要把 review 意见和逐条裁决原样累加成正文。

## 标准文档结构

单 PR spec 默认保留以下八章及顺序，作为稳定的评审入口。文档标题下的一级章节使用 `## 1. …`；章内组织随任务调整。

| 章节 | 本章职责 |
|---|---|
| 1. 背景与问题 | 介绍任务、场景、现状与缺口，提供支撑问题判断的代码证据。 |
| 2. 设计目标与范围 | 定义功能与性能目标、约束、交付范围及非目标。 |
| 3. 概念与功能说明 | 解释必要概念，用贯穿示例说明使用方式、接口或配置、正常与异常结果。内部任务面向调用者，不虚构用户界面。 |
| 4. 方案设计 | 先写总体架构与核心流程、组件职责与所有权，再按关键机制展开详细设计，解释状态转换和交接。 |
| 5. 设计取舍 | 结合负载、产品与部署约束比较替代方案，说明收益、代价、缺点及成熟系统的借鉴边界。 |
| 6. 稳定性与兼容性 | 说明相关的并发、取消、失败恢复、迁移兼容，以及对其他功能的影响。 |
| 7. 可观测性与验收 | 将目标对应到可观察的功能、异常和性能结果，说明诊断线索与适用的生产形态。 |
| 8. 未决问题与后续衔接 | 区分待裁决事项、可留给 plan 的局部选择与后续工作，记录依赖、交接和相关文档入口。 |

第 4 章默认以 `4.1 总体架构与核心流程`、`4.2 组件职责与所有权` 开始，后续子节使用具体机制名称。
Spec 的详细设计要足以判断机制是否正确；plan 再落实代码结构、修改顺序与验证命令，不能把所有机制解释都推给 plan。

一级章节默认保留；确实不适用时，用一句话说明原因，不编造内容。用户或项目另有明确结构要求时遵循该要求。
新增 review 意见整合到对应章节，不在末尾不断追加孤立裁决。Umbrella 继续使用独立模板及 contract 的面板约定。

分清当前行为、目标态和假设，代码锚点放在其支持的解释附近。未知的默认值和性能数值不编造；成熟系统的局部实现
不能用于推断整个系统。章内采用连贯段落、必要的表格和图，不要求把每项写作提示复制为列表。

不要把尚未决定的接口名、文件拆分或实现步骤写成既定设计。明确区分“设计契约”和“计划阶段可决定的实现细节”。

## 完成检查

- 文档位于 `DOC_ROOT/workflow/` 下对应子目录（`specs/` 或 `umbrella/`）；
- frontmatter 可解析；项目启用 Roadmap 时，对应字段完整；
- 单 PR spec 的八章可定位，各章完成其职责；不适用内容说明原因，结构例外有用户或项目依据；
- spec 粒度可由一个 PR 独立验收，或 umbrella 明确拆出子任务；
- 所有关键现状结论都能追溯到当前代码；
- 未参与讨论的读者能从开头说清任务、问题、目标，并沿示例理解机制和取舍；
- 正文说明了裁决之间的因果，未把术语、路径或 review 历史当作解释；
- 验收标准描述行为，不用旧符号缺失、精确文件数或迁移编号作永久 guard；
- 项目启用 umbrella 时，更新必要的面板、反链和阶段图；
- 没有同时开始 plan 或实现。

完成后向用户报告文档路径、核心裁决，并说明下一阶段是在当前可编辑模式中直接编写和落盘实现 plan。
